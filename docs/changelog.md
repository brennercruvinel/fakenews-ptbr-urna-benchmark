## Unreleased

- CI runs the checks of mtg-urna-benchmark (#9): setup-uv pinned to a commit SHA with its version in a comment, as Urna pins third-party actions; `uv lock --check` (the locked env carries torch, which no check needs, so CI does not sync it); `uvx ruff check benchmark` instead of an unpinned `pip install ruff`; the tracked build locks and manifests checked against their `SHA256SUMS`; `render_report.py --check` without the file guard that always passed. It runs on pull requests and on pushes to main, once per pull request instead of twice.
- The download commands name a hub revision (#8): `hf download` in the README and the card, and the card's three `load_dataset` calls, take `f3ddaef1`, the hub commit that published the v0.1 files on corpus e884b982. The 59 files under `data/` and `release/` are the same there as on today's main, so the pin changes nothing a reader gets now, and a later hub change cannot change it. Checked: the pinned `hf download` gives `minilm-exact/SHA256SUMS` byte-identical to this repo's, and `load_dataset` at that revision gives 2,601 queries and 4,582 qrels. The card follows in hub pull request #8.
- `CITATION.cff` cites this benchmark (#7). It described Urna 0.5.1 (`title: Urna`, `type: software`, the 0.5.1 crates.io and release URLs), so GitHub's "Cite this repository" and the hub copy cited the engine instead of the dataset. It now follows mtg-urna-benchmark: the benchmark as the work (`type: dataset`, version 0.1.0, released 2026-10-02, the corpus_hash as identifier), Urna under `references` with the version that built the v0.1 files (0.5.1), and the sources' licenses pointed at `docs/sources.md`. The hub copy is the same file (hub pull request #7). `cffconvert --validate` passes.
- Pin Urna 0.5.4, the published release, instead of 0.5.1 (`pyproject.toml`, `uv.lock`) (#6). Nothing measured here changes: the benchmark calls `urna.build`, `search`, `search_ann` and `search_hybrid` from the Python API, which did not change from 0.5.1 to 0.5.4, and the potion table in the two wheels is byte-identical (same `model_hash`, `model.safetensors` and `tokenizer.json`). The v0.1 numbers keep the version that measured them: experiments 02 and 03 now say urna 0.5.1 in their provenance, as the build locks and experiment 04 already did, and `profiles/models.toml` keeps potion's `revision = "urna==0.5.1"`, the wheel the v0.1 builds used. `check_clean.sh` ran again from a fresh clone of the pull request's commit `3ca030d`, with the 0.5.4 wheel and the 0.5.4 CLI from the release archive: every check passed, and the potion and minilm `exact` rebuilds have the release's `file_hash` (`b044723b`, `4bcb8e0f`). Experiment 04 records that run.

- The retrieval method said the files are searched the way the Urna CLI routes them, beam max(100, k). Urna 0.5.1 sent hybrid files down HNSW; 0.5.3 and later route them by what the file carries, which is what `evaluate.py` does, and the HNSW beam is widened to the file's floor of 400 (its `ef_construction`). The text says so; the numbers are the same.
